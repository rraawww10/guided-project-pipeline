================================================================================
0. HEADLINE
================================================================================

Two projects shipped, all six gates approved, 39/39 acceptance criteria green,
zero tickets raised, zero builder retries, zero verifier retries.

And yet 19 distinct blockers were hit. 17 of the ~19 lived in Phase 1 (the
spec). Phase 2 (the code) produced no real failures at all.

The pipeline is very good at catching things that are cheap to fix and blind to
everything that is expensive.


================================================================================
1. THE ONE NUMBER THAT REFRAMES EVERYTHING
================================================================================

THE SPEC LINTER HAS NEVER REJECTED A SPEC. NOT ONCE.

Every lint.json across all six rounds of both projects reads:

    ok = true, error_count = 0, warning_count = 0, errors = []

  projects/recipe-box/.pipeline/round-1/lint.json    clean  -> REJECTED at Gate 1
  projects/recipe-box/.pipeline/round-2/lint.json    clean  -> REJECTED at Gate 1
  projects/recipe-box/.pipeline/round-3/lint.json    clean  -> REJECTED at Gate 1
  projects/recipe-box/lint.json          (round 4)   clean  -> approved
  projects/tip-split/.pipeline/round-1/lint.json     clean  -> REJECTED at Gate 1
  projects/tip-split/lint.json           (round 2)   clean  -> approved

Four of those clean specs were then rejected on 17 BLOCKING findings:

    recipe-box round 1     4 blocking   (A1-A4)
    recipe-box round 2     4 blocking   (A1-A4)
    recipe-box round 3     6 blocking   (A1-A4, B1-B2)
    tip-split  round 1     3 blocking   (B1-B3)
    ----------------------------------------
    TOTAL                 17 blocking, every one after a clean linter

Consequences, all three load-bearing:

  1. Rule 1's checker for the Spec Writer has a 0% CATCH RATE to date.
  2. The Spec Writer <-> linter retry loop HAS NEVER EXECUTED ONCE. The
     "retries: spec=0/15" on both projects means "the checker never fired",
     NOT "the spec was good".
  3. 100% of spec defects were caught by a person reading ~70 KB of documents
     (spec.md 34-38 KB + spec.json 25-30 KB + ambiguity.md 7-11 KB).

This is the root cause of most of section 5. Every Phase 1 blocker below is a
symptom of it.

PHASE 0 - INFRASTRUCTURE. Hit before any project completed.
--------------------------------------------------------------------------------

B-01  Relative interpreter path combined with cwd=project
      WHAT   The test runner passed a relative interpreter path while setting
             cwd=project, so the path resolved against the NEW directory and
             vanished. Fixed by resolving in all five scripts.
      WHY IT MATTERED  The nightly watchdog builds paths from Path("."), so
             every scheduled run would have died this way.
      WHY IT ESCAPED   The selftest's fixtures use absolute tempdirs, so no
             relative-path bug can ever fail it. The bug class is
             STRUCTURALLY INVISIBLE to the selftest.
      PHASE  Scripts / test runner
      RECURRENCE  Fixed. The CLASS recurs - the blind spot is still open.

B-02  python -m venv fails on Debian
      WHAT   Debian splits ensurepip into the python3-venv package, so
             venv creation failed outright.
      FIX    ensure_venv() now tries uv, then stdlib venv, then
             venv --without-pip plus a get-pip bootstrap, and names the apt
             fix if all three fail.
      PHASE  Scripts / test runner
      RECURRENCE  HIGH on any new machine or CI box. Note the last fallback
             needs NETWORK to fetch get-pip - it will fail closed offline.

PHASE 1 - THE SPEC. 17 of ~19 blockers live here.
--------------------------------------------------------------------------------
Spec CONTENT defects are grouped by recurring shape in section 3.
The entries below are failures of the MACHINERY around the spec.

B-03  The Gate 1 loop does not terminate
      WHAT   The Spec Breaker returned blocking findings on ALL FIVE passes it
             ever made. Round ambiguity reports held 11, 13 and 11 findings.
             A policy of "reject until blocking == 0" provably never ends.
      WORKED AROUND  A stopping rule had to be invented mid-flight and was
             written into round-3/why.md before the next report was read:
             "approve when every remaining finding sits in a column a
             downstream checker owns."
             Round 3 had five findings no checker could see -> reject.
             Round 4 had one, with a two-sentence fix -> apply by hand, approve.
             The COUNT was similar both times; only the column mattered.
      LESSON Declare the stopping rule BEFORE the pass, not after - deciding it
             while holding the next report invites moving the line to fit the
             answer.
      PHASE  Gate 1
      RECURRENCE  CERTAIN, every project. The rule exists in prose only;
             nothing forces the Breaker or the gate reader to use it.

B-04  A stale ambiguity report was trusted as current
      WHAT   `revise` deliberately uses shutil.move so a rejected round's
             ambiguity.md cannot linger (comment at cli.py:239 says so).
             Someone copied round 2's report back into the project root
             afterwards. `pipeline next` reads progress off the files PRESENT,
             so it reported "Gate 1" for a ROUND-3 SPEC THE SPEC BREAKER HAD
             NEVER READ.
      COST   The gate reader spent a full pass walking four findings that had
             already been fixed.
      ROOT CAUSE  Nothing ties a report to the spec it reviewed.
      INTERIM MITIGATION  Check ambiguity.md's mtime against spec.md's before
             trusting it.
      PHASE  Gate 1 / step 3
      RECURRENCE  HIGH. No hash, no binding, no check.

B-05  A finished agent woke up and re-ran, overwriting the spec
      WHAT   The round-4 Spec Writer reported a SECOND time, over an hour after
             it had finished, saying it had copied .pipeline/round-3/spec.md
             over the live files and re-derived its fixes.
      WHY IT DID NOT CORRUPT THE BUILD  Only the mtimes cleared it - the spec
             was last written 13 minutes before the Builder ran.
      ROOT CAUSE  pipeline/guard.py restricts writes only while a LOCK exists,
             and Phase 1 sets NO LOCK AT ALL. spec.md and spec.json are
             writable at every step of Phase 1.
      RISK   A re-run landing after Gate 1 would have silently replaced the
             approved spec with a rejected one, and only mtimes would show it.
      PHASE  Phase 1 / step 2
      RECURRENCE  Unpredictable but non-zero, and COMPLETELY UNGUARDED.

B-06  The approved spec existed only in the working tree
      WHAT   app/ and verify/ were built against a round-4 spec that existed
             only in the working tree. HEAD still held the round-3 spec that
             had been REJECTED.
      ROOT CAUSE  There is no archive-on-approval step. `revise` archives only
             on REJECTION.
      RISK   A single overwrite would have left a green 22/22 build with no
             readable record of what it was built to do.
      PHASE  Gate 1 -> Phase 2 boundary
      RECURRENCE  HIGH until a step commits or archives the spec at approval.

B-07  The spec was edited AFTER the code was built
      WHAT   recipe-box state.json logs `lint` at 06:33:42 and 06:35:21 -
             after `test:app` had already finished at 06:18:27.
      ROOT CAUSE  gp-phase2-code.js calls lock('off') before EVERY test run
             (line 143 unlocks at the end of each retry iteration), so an
             unlocked window exists in every single iteration.
      PHASE  Phase 2
      RECURRENCE  The window is structural - it opens on every run.

B-08  learning/lessons.md was edited mid-run
      WHAT   The file was written during recipe-box round 2. The Spec Breaker
             read it EMPTY at step 3, noticed it change, and re-checked every
             finding.
      COST   A full Breaker pass, and it could have gone the other way.
      RULE   Update lessons.md BETWEEN runs, never during one.
      PHASE  Step 3 / shared inputs
      RECURRENCE  CERTAIN whenever two things run concurrently. Nothing
             enforces it.

PHASE 2 - THE CODE. The phase that gave almost no trouble.
--------------------------------------------------------------------------------
Recorded because it INVERTS Flow.md's central cost assumption.

B-09  Flow.md's cost model is wrong for low-retry runs
      CLAIM  Flow.md: the Builder is 80-90% of agent cost "because it re-reads
             the codebase on every retry".
      MEASURED (tip-split)  Builder 8.3 min of 53 min of workflow wall time
             = 16%. The SPEC PHASE was 55%, because it ran twice. The Spec
             Breaker alone cost more than the Builder.
      WHY    The claim is conditional on retries actually happening. Both runs
             had ZERO code retries (0 builder, 0 verifier; 22/22 and 17/17
             green on the first test run).
      IMPACT Review time and optimisation effort were pointed at the wrong
             phase.
      PHASE  Phase 2 / planning
      RECURRENCE  The Builder becomes the cost centre only once retries start.

B-10  All-green churn is invisible to the retry circuit breaker
      WHAT   recipe-box logged 6 `test:app` runs (5 of them inside 60 seconds)
             and 10 `lint` runs, with retries showing spec=0/15, code=0/15.
      ROOT CAUSE  state.burn_retry() is called ONLY on checker FAILURE
             (cli.py:79 for lint, cli.py:92 for test). Successful re-runs burn
             nothing. Separately, the workflow's own `attempt` variable is
             LOCAL JS STATE and resets to 0 on every re-invocation.
      RISK   Rule 6 guards against a FAILING loop, not a passing-but-repeating
             one. A run that thrashes while every checker stays green burns
             unbounded agent budget without tripping the stop or raising a
             ticket.
      PHASE  Phases 1-3 / state.py
      RECURRENCE  Open. Already observed twice.

B-11  An accepted spec risk that happened not to bite
      WHAT   tip-split Gate 1 was approved with finding A1 outstanding:
             spec.md overclaimed that a share row reads "Person 1 R341.00"
             however the Builder nests it, which is false under Playwright
             to_have_text. Risk: up to 4 session-3 criteria red.
      OUTCOME  Never bit - the Builder hand-verified the share-row markup
             before the Verifier wrote its tests.
      WHY ACCEPTED  It surfaces at step 6 where the Builder/test-runner loop
             fixes it for free, unlike round-1 B1 which would have escaped to
             the cutter at step 8.
      PHASE  Gate 1 -> Phase 2
      RECURRENCE  This is the stopping rule (B-03) working as intended.
             Logged as a correct call, not a defect.

      WHAT   Nothing before the Pack Writer measures teaching minutes. The
             linter caps cuts and criteria per session but weighs neither
             setup cost nor minutes.
      OBSERVED  tip-split  session 1: 45 min against a 40 min cap
                           (4 cuts PLUS the project's entire setup, while
                            session 3 carried 3 cuts and no setup)
                recipe-box session 3: 45 min against the 40 min cap

      RULE OF THUMB  The session holding the setup should carry FEWER cuts

B-14  deploy_check.py passes `install` over a live CVE

3. RECURRING SPEC DEFECT SHAPES
================================================================================
The 17 blocking Gate 1 findings are NOT 17 unique problems. They are seven
shapes that keep coming back. Sources: round-*/why.md.

S-a  CUT MARKERS THAT SWALLOW A FUNCTION'S ONLY `return`  (TS2355)
     recipe-box R1 A1: SIX cuts did this.
     tip-split  R1 B1: skeleton_rules[1] forced a return inside the markers for
                BOTH route handlers - the exact same shape, on the very next
                project, with the lesson already written down.
     SEVERITY  Worst possible failure mode. The skeleton does not COMPILE.
               Not one red test - NO BUILD AT ALL, and the student's whole app
               stops working.
     FIX PATTERN (proven both ways in fixtures/runner-check):
               keep the return OUTSIDE the markers, declare a typed fallback
               above, and cut only the assignment that feeds it.

                 export async function GET(): Promise<Response> {
                   let body: { ok: boolean } = { ok: false }
                   let status = 501
                   // >>> CUT cut-api-health
                   body = { ok: true }
                   status = 200
                   // <<< CUT cut-api-health
                   return Response.json(body, { status })
                 }

     ALSO      The fallback must NOT accidentally pass the test. A 501 and
               ok:false fail the criterion, which is what the skeleton needs.
               A fallback returning plausible data makes the test green on an
               empty skeleton.
     RECURRENCE  NEAR-CERTAIN. It is the natural way to write a handler, and
               it already recurred across consecutive projects.

S-b  UNOWNED FETCHES / SESSION-BOUNDARY ERRORS
     recipe-box R1 A2  tags fetch unowned in session 1
     recipe-box R2 A2  refetch unowned by any session-2 cut
     RULE  Every fetch needs an owner. A screen built in session 1 whose data
           comes from an endpoint built in session 2 leaves session 1's
           skeleton throwing.

S-c  UNPINNED SELECTORS / TEXT THAT IS AMBIGUOUS ON SCREEN
     recipe-box R1 A3  no selectors pinned for UI criteria
     recipe-box R1 A4  "baking chip" names THREE elements on the page
     recipe-box R2 A4  search box controlled vs uncontrolled unstated
     tip-split  R1 B3  c-1-2 must pin the count of 6
     WHY SYSTEMIC  With CSS modules the class names are hashed, so any
           criterion that counts or reads something on screen must pin an
           exact string or a stable hook (data-testid on the repeated
           element - it survives styling changes and reads the same in the
           skeleton). Otherwise the Verifier guesses from the Builder's
           markup, and the student then rewrites exactly that markup from a
           hint that never mentions it.
     ALSO  A number in a criterion must be unambiguous on the page.
           "renders 2 cards" is fine. "after the baking chip is clicked" is
           not, when three elements read "baking".

S-d  CUTS THAT WRITE SHARED STATE AND WIPE EACH OTHER
     recipe-box R2 A1  the hint "write the search text into the q parameter"
           is fully satisfied by router.replace('/?q=' + text), which WIPES
           the active tag. And no criterion drove both filters together
           through the UI.
     RULES  If a cut writes to shared state, its hint must say what to
           PRESERVE. And test the COMBINATION, not just each half - testing
           two filters at the endpoint does not cover the screen that builds
           the URL.

S-e  BYPASSABLE OR VACUOUS GRADING CUTS  <-- the dangerous class
     recipe-box R3 A1  hardcoded chips void cut-api-tags-list as a grading cut
                       for c-2-5/c-2-6
     recipe-box R3 A3  c-1-2 asserts per-element shape, so it passes VACUOUSLY
                       over the [] fallback with cut-store-read-all open - an
                       undocumented third subset case
     recipe-box R3 B1  cut-recipe-scale-quantity does not name scaleQuantity,
                       so cut-fraction-scale is BYPASSABLE with c-4-2/3/4 green
     tip-split  R1 B2  c-3-4 must fail on an inert setter
     WHY WORST  These ship SILENTLY. No test goes red. The grading is simply
           wrong, and no downstream checker can see it.

S-f  HINT UNDER-SPECIFICATION
     recipe-box R3 A2  the cut-api-recipes-list hint names neither "all" nor
           "shown", though rule 2 puts both in scope. Session 1 goes green on
           "all" and then FIVE OF SESSION 2's SIX CRITERIA FAIL ON CORRECT
           STUDENT WORK.
     KEY LINE from why.md: "this hint is the whole text the student gets."
     NOTE  Fixing A4 (session rebalance) also DISSOLVED A2 - findings are not
           independent, so fix the structural one first.

S-g  SESSION IMBALANCE
     recipe-box R3 A4  session 1 carried lib/types, the 8-recipe seed, the
           store, fractions, page and RecipeList PLUS 4 cuts, against session
           4's 3 cuts and no setup - "the tip-split lesson verbatim, caught
           only at step 9".
     See B-13. Detected at step 9, root cause at step 2.

4. BOTTLENECKS
================================================================================

THE HEADLINE COMPARISON

                              tip-split                recipe-box
                              (gates auto-approved)    (real gate reads)
  End-to-end wall clock       66 min                   23 h 20 min
  Spec rounds                 2                        4  (5 Breaker passes)
  Phase 1 (idea -> Gate 1)    31 min                   20 h 01 min
  Phase 2 (Gate 1 -> Gate 2)  19 min                   1 h 10 min
  Phase 3 (Gate 2 -> ship)    16 min                   2 h 09 min

  A 20x difference, almost entirely the human at the gates.


BN-1  GATE 1 AND THE SPEC LOOP  -  dominant bottleneck today
      recipe-box spent 20 of its 23 hours in Phase 1. Strip the single
      17 h 55 m overnight wait (11:05 on 08-26 -> 05:00 on 08-27) and Phase 1
      STILL cost ~2 h 06 m of active time - more than Phases 2 and 3 combined.
      Structural, not bad luck, because of B-03 + B-16 + section 1: the Breaker
      never returns clean, and the cheap checker absorbs none of the load.
      Each rejected round costs a full Spec Writer + linter + Breaker cycle
      PLUS a human pass over ~70 KB.

BN-2  HUMAN READ BANDWIDTH AT 3 BLOCKING GATES  -  the throughput ceiling
      Three gates per project, all serialized, all blocking BY DESIGN ("a
      workflow cannot block on a person", so each phase ends at its gate and
      stops). Measured human gate time on recipe-box, from the timestamps:

        Gate 1 rejection 1   lint 10:12:45 -> revise 10:30:03   17 min
        Gate 1 rejection 2   lint 10:40:39 -> revise 10:52:29   12 min
        Gate 1 rejection 3   lint 11:05:25 -> revise 05:22:35   22 min + overnight
        Gate 3 read          deploy 07:25:06 -> gate3 09:07:45  1 h 42 min
        ---------------------------------------------------------------
        TOTAL                                          ~2 h 33 min, 4 sittings

      Read load per project: ~70 KB of spec + ambiguity, plus 912 lines of pack
      (recipe-box) or 1,406 (tip-split).
      THROUGHPUT = reader-hours / ~2.5 h per project. It does NOT amortize.
      Machine work gets cheaper per project; gate reading does not. The depth
      is real - recipe-box's Gate 1 note is ~1,800 characters of dense
      reasoning about a single finding's blast radius.

BN-3  THE APPROVED SPEC IS UNPROTECTED  -  a REWORK bottleneck
      B-05 + B-06 + B-07 together. guard.py restricts writes only while a LOCK
      exists; Phase 1 sets none, and Phase 2 unlocks before every test run.
      Cost when it fires is not delay but INVALIDATION - a late spec change
      voids the code, the tests, the skeleton, and the gates already passed.

BN-4  DEFECTS THAT SURFACE AT STEP 9, WHERE THE FIX INVALIDATES EVERYTHING
      B-13. Both projects overran; neither was fixed. The repair loop is
      longer than the team's willingness to pay, so the pipeline ships known
      defects. Will recur on every project until something before step 4
      weighs setup cost and minutes.

BN-5  CHECKER BLIND SPOTS THAT CONVERT DIRECTLY INTO GATE TIME
      Every place a script says "ok" while a human must check by hand feeds
      BN-2:  B-12 (partial cut states), B-14 (CVE), B-04 (report/spec binding),
      and section 1 (the linter as a whole).

BN-6  THE CIRCUIT BREAKER DOES NOT COUNT GREEN CHURN
      B-10. Rule 6 protects against a failing loop, not a thrashing green one.

BN-7  AGENT OVERHEAD PER PHASE
      B-15. 5-6 agents per phase, of which 2-3 do real work; the rest exist to
      run a single shell command. Adds latency, cost, and a guaranteed
      false-positive security warning on every run.

BN-8  INFRASTRUCTURE
      B-18. Not biting yet. Will bite around 20+ projects.

The pattern is unambiguous:

  Phase 2 has a REAL checker (boot the app, run the suite, pass/fail is not an
  opinion) and produced ZERO escapes across both projects.

  Phase 1 has a checker that HAS NEVER FIRED and produced EVERY blocker.

  Phase 3's checkers pass over their own KNOWN blind spots.

Conclusion: the difference between the phases is not the difficulty of the work.
It is whether the checker can actually see the defect class it is supposed to
catch.
