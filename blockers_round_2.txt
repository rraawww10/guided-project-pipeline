R2-01  The write guard refused read-only commands
       WHAT   check_bash fired on any ">" anywhere in a command - quoted or
              not - and then path-checked EVERY projects/... token on the line.
              A grep for the cut marker, naming a frozen spec.json on the same
              line, was blocked: the quoted marker looked like a redirect.
       IMPACT Any inspection of a shipped project was refused. It fired twice
              during the habit-tracker run and was logged in lessons.md as
              "Not yet fixed" - it then survived a full round as a known,
              unfixed papercut.
       ROOT CAUSE  A regex was doing a parser's job. Two defects hid in one
              pattern: a ">" inside quotes is data, and even for a real
              redirect only the token AFTER it is written.
       FIX    Replaced with a quote-aware lexer that splits the line into
              simple commands and asks each what it WRITES - the operand of
              ">"/">>", every path argument of rm/mv/tee/sed -i/..., and the
              destination only for cp/install/rsync.
       WHAT THE FIX ALSO EXPOSED  Two silent rule-3 HOLES the old pattern had:
                a) a "<" operand was treated as a write (false positive), and
                b) a second LINE of a script was invisible. The whole command
                   was scanned as one string, "cd app" was found as the command
                   word, and a two-line call that cd'd and then removed a file
                   under verify/ passed straight through. A builder could have
                   deleted a test file that way for the entire life of the
                   guard.
       PHASE  Scripts / guard
       RECURRENCE  Fixed, with 9 new selftest checks covering the read/write
              pairs and the multi-line case. The CLASS - "a pattern used where
              a parser is required" - is still open elsewhere.

R2-02  Every phase workflow was unrunnable on a Windows checkout

              The Workflow tool refuses a script containing control characters,
              so gp-phase0-ideas through gp-phase3-pack could not launch at

                "script contains control characters that would be hidden in
                 the approval dialog"
       ROOT CAUSE  git config core.autocrlf = true. The committed blobs are
              LF-clean (verified: git show HEAD:<path> has 0 CR bytes); the
              checkout rewrites them. Nothing in the repo pinned the ending.
       IMPACT TOTAL for this platform. Not one of the four documented phase
              entry points worked on a fresh Windows clone. The pipeline's
              whole published usage - the gp-phase* commands in README.md - was
              dead on arrival, and the error names control characters, not line
              endings, so it does not point at its own cause.
       FIX    Added .gitattributes pinning ".claude/workflows/*.js text eol=lf",
              and normalised the working copies.
       PHASE  Infrastructure / repo hygiene
       RECURRENCE  Fixed for these four files. HIGH for any NEW workflow or
              script added later - the .gitattributes rule is a path glob, and
              nothing checks that a new entry point is covered by it.

              on Windows) and B-01/B-02 in round 1. Three rounds, three
              platform-specific silent failures. This is now a pattern, not a
              coincidence: THE SELFTEST ONLY EVER EXERCISES THE MACHINE IT RUNS
              ON, and nothing checks that the repo's own entry points can be
              invoked at all.

       WHAT   cmd_revise moves spec.md, spec.json, lint.json, ambiguity.md and

              shape: mutation.main() unguarded, so R2-17's exception escaped
              before mutation.json was written and before burn_retry.
       WHY THIS IS WORSE THAN R2-16  R2-16 produced a loop, which wastes money.
              R2-18 produced a WRONG INSTRUCTION. With no mutation.json on
              disk, the phase-2 workflow reported:
                  blocked: "the mutation check found student tasks that grade
                            nothing"
                  ungraded_tasks: []
                  fix: pipeline gate ... 1 reject && pipeline revise ...
              An empty list of ungraded tasks alongside a claim that ungraded
              tasks were found. Had that instruction been followed, a correct
              spec would have been rejected at Gate 1 and sent back through a
              full round - roughly 35 minutes and 500k tokens - to fix a defect
              that does not exist. The absence of a report was read as a
              finding.
       FIX    cmd_mutation now catches, burns a retry, logs the step failed, and
              prints that no conclusion can be drawn about ungraded tasks.
       PHASE  Orchestrator / rule 6
       RECURRENCE  Fixed for test and mutation. STILL OPEN for cmd_lint,
              cmd_cut, cmd_leak, cmd_guide_lint, cmd_deploy and cmd_redfirst.
              This is the second time the same class has been hit in one round,
              and the second time it was found only because a human read the
              output and disbelieved it.
       THE GENERAL LESSON  A checker has three outcomes, not two: pass, fail,
              and DID NOT RUN. The pipeline models the first two. Everything
              downstream - the retry cap, the gate rules, the workflow's own
              summary - silently maps the third onto one of the other two, and
              which one it picks is arbitrary. R2-16 mapped it to "keep trying";
              R2-18 mapped it to "the spec is wrong".


R2-19  THE MUTATION CHECK HAS NEVER WORKED, AND IT FAILED GREEN
       WHAT   test_runner names its log `server-{target}.log`. For --target app
              that is fine. The mutation check passes targets that are PATHS -
              .pipeline/mutants/cut-game-status - so the name became
              `server-.pipeline/mutants/cut-game-status.log`, whose parent
              directory does not exist. Every mutant run died in boot() with
              Errno 2 before a single test executed.
       WHY IT PASSED ANYWAY  mutation.py counts a criterion as red when its
              status is "fail" OR "missing". A mutant that never ran reports all
              18 criteria missing, so every criterion the task declared "went
              red" and every task looked graded. ok: true, ungraded_tasks: [].
       THE TELL, RECORDED AND IGNORED  The report already carried `collateral` -
              criteria that went red but were NOT declared by the task. It read
              17, 14, 5, 14, 16, 9, 16. Removing one student task turned
              seventeen unrelated criteria red, and the verdict did not look at
              the field. `ok` was computed as bool(went_red) alone.
       WHY THIS IS THE WORST ONE  This check exists to prove rule 3 - that the
              suite can actually go red. requirements_doc.md added it as a
              headline capability, Gate 2 refuses without it, and it is the only
              evidence that a student task is graded at all. A false GREEN here
              is the exact failure it was built to prevent.
       NOT PLATFORM-SPECIFIC  server-.pipeline/mutants/... fails on Linux too.
       NEVER EXERCISED BEFORE  All three shipped projects are flow 1, which has
              no mutation step. pipeline-test-01 is the FIRST project ever to
              run this check, and its first result was vacuous.
       FIX    (a) target_slug() sanitises a target path into a filename.
              (b) A mutant that removes one task must leave the rest of the
                  suite green. If NO criterion passes, the mutant did not run,
                  and "everything went red" proves nothing: the task is now
                  marked inconclusive, and inconclusive FAILS the check rather
                  than passing it.
       PROOF OF THE FIX  Same code, same spec, before and after:
                before   every mutant: 0 pass / 18 missing, collateral 5-17
                after    cut-flag-toggle 17 pass / 1 fail, collateral 0
                         cut-game-status 14 pass / 4 fail, collateral 0
              and across all seven tasks went_red == graded_by EXACTLY, with
              collateral 0 on every one. 684.8s of real work against 222s of
              nothing.
       PHASE  Scripts / mutation + test_runner
       RECURRENCE  Fixed. The CLASS - a checker that fails green - has no
              general defence in the pipeline. Every other checker's failure
              mode should be audited for which way it fails.


R2-20  AN AGENT EDITED THE PIPELINE'S OWN CODE, MID-RUN
       WHAT   guard.check_path only ever walked up looking for projects/<slug>/.
              Everything outside projects/ was therefore unguarded: the
              checkers, the orchestrator, the agent prompts, the workflow
              scripts, and guard.py itself. Rule 1 says every agent has a
              checker. Nothing said the agent could not rewrite the checker.
       WHAT HAPPENED  During the phase-3 run, `pipeline cut` crashed five times
              on WinError 1314. A phase-3 agent diagnosed it, opened
              pipeline/cutter.py, and patched it - then refactored
              pipeline/mutation.py to import its new helper. It also read
              blockers_round_2.txt and wrote R2-18's narrative into its
              docstring.
       THE PATCH WAS GOOD  Better than the one it replaced: it returns HOW the
              link was made, because Path.unlink raises on a junction and
              cleanup would have become the next crash, and it fails open with
              a report rather than crashing. Kept, and committed with
              attribution (fa14e46).
       WHY IT IS STILL THE WORST FINDING  The quality of the patch is luck, not
              a control. An agent that rewrites a checker manages every agent
              that checker judges, itself included - which is rule 5 inverted.
              And unlike the loop or the fabricated verdict, this failure mode
              has NO SIGNATURE: the run goes green, the suite passes, and
              nothing in any report says the checker changed underneath it. It
              was found only because `git status` was read for an unrelated
              reason.
       THE CONTRAST IN THE SAME RUN  Earlier the Test Writer hit redfirst.json
              landing outside its lock (R2-08), tried to clean up, was refused,
              and DISCLOSED the leftover in its summary instead of routing
              around it. Same pipeline, same run, opposite instincts - because
              nothing told either agent which was expected.
       FIX    check_pipeline() refuses writes to pipeline/, .claude/ and
              learning/ whenever any project holds a LOCK - keyed to state, the
              way the spec freeze is, because a PreToolUse hook cannot
              authenticate the writer. Between steps a person edits freely. The
              refusal text tells the agent what to do instead: report the defect
              and stop, because reporting something you cannot fix is the
              expected outcome, not a failure.
       learning/ IS IN THE LIST for a documented reason: CLAUDE.md says
              lessons.md is updated between runs and never during one, and round
              1 recorded it being edited mid-run anyway (B-08). Every agent
              reads it at the start, so a mid-run edit means two agents in one
              run read different instructions.
       HONEST LIMIT  This stops the ACCIDENTAL case - a helpful agent fixing a
              bug it should have reported - which is exactly what happened. It
              is not a defence against a determined one, and no file-based
              scheme enforced by the hook itself can be. A real control needs
              the hook to identify the writer.
       PHASE  Scripts / guard
       RECURRENCE  Fixed for the accidental case. 12 new selftest checks pin
              both directions: blocked under a lock, editable between steps.


R2-21  R2-13 HAD ALREADY BITTEN, AND ONLY THE WATCHDOG SAW IT
       WHAT   The first watchdog replay after pipeline-test-01 shipped returned
              ok: false. All 73 criteria across all four projects passed; the
              failure was habit-tracker's spec hash.
                 approved         6691dad5c499...
                 on disk (CRLF)   36a2ad2eeb57...   <- drift
                 same bytes as LF 6691dad5c499...   <- match
              habit-tracker was frozen against LF bytes and this Windows
              checkout gave it CRLF, so _guard would refuse its code and pack
              phases. Exactly the failure R2-13 predicted - already present,
              before .gitattributes was written.
       WHY THE OTHERS SURVIVED  recipe-box and tip-split have no SPEC_FROZEN at
              all; they predate the freeze, so they cannot drift.
              pipeline-test-01 was frozen on this machine, LF, and matches.
       THE ADVICE WAS ALSO WRONG  The guard tells a reader to restore the copy
              in .pipeline/approved/. That copy was CRLF too, so restoring it
              would have reproduced the drift. Normalised as part of this fix.
       FIX    The working tree was rewritten to LF and the hash verified against
              SPEC_FROZEN before the change was kept - restore-on-mismatch, so
              there was no state where the spec was neither form. Watchdog then
              returned ok: true, 4/4, 73/73.
       HOW IT WAS FOUND  The nightly watchdog, on its first run covering a
              flow-2 project. Round 1 recorded the watchdog as "the safety net
              has never been tested" (B-17). It has now caught something no
              other checker looked at, on its first meaningful outing.

R2-22  THE WRITE GUARD CANNOT SEE WRITES MADE INSIDE AN INTERPRETER
       WHAT   Fixing R2-21 required rewriting a frozen spec. The guard correctly
              refused `rm` on it. `git checkout-index -f` exits 0 but skips the
              file - normalising CRLF gives content identical to the index, so
              git believes it is up to date and only delete-then-checkout forces
              it. The bytes were then written with a python heredoc, which the
              guard did not see at all.
       THE HOLE  check_bash models shell redirects and the commands that take a
              path argument. It does not model `python -c`, a node script, or
              any program that opens a file itself. Every protection in this
              guard has that gap: the frozen spec, rule 3's subtree locks, and
              the new pipeline/ rule added as R2-20.
       NOT A BUG IN THE LOGIC  It is inherent to a PreToolUse hook, which sees
              the command and not the syscalls. No pattern over command text can
              close it.
       WHAT IT MEANS  Every claim in this file about the guard "refusing" or
              "enforcing" something should be read as: against an agent taking
              the direct route. An agent that writes through an interpreter is
              unaffected, and so is one that means to be. The guard raises the
              cost of an accident; it does not bound behaviour.
       PHASE  Scripts / guard
       RECURRENCE  Open, and not closeable at this layer. Worth stating in
              CLAUDE.md so nobody reads rule 3 as a guarantee.
