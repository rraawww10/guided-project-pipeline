INFRASTRUCTURE - hit before the pipeline could run at all

R2-01  The write guard refused read-only commands
       WHAT   check_bash fired on any ">" anywhere in a command - quoted or
              not - and then path-checked EVERY projects/... token on the line.
              A grep for the cut marker, naming a frozen spec.json on the same
              line, was blocked: the quoted marker looked like a redirect.
       IMPACT Any inspection of a shipped project was refused. It fired twice
              during the habit-tracker run and was logged in lessons.md as
              "Not yet fixed" - it then survived a full round as a known,
              unfixed papercut.
       ROOT CAUSE  A regex was doing a parser's job. Two defects hid in one
              pattern: a ">" inside quotes is data, and even for a real
              redirect only the token AFTER it is written.
       FIX    Replaced with a quote-aware lexer that splits the line into
              simple commands and asks each what it WRITES - the operand of
              ">"/">>", every path argument of rm/mv/tee/sed -i/..., and the
              destination only for cp/install/rsync.
       WHAT THE FIX ALSO EXPOSED  Two silent rule-3 HOLES the old pattern had:
                a) a "<" operand was treated as a write (false positive), and
                b) a second LINE of a script was invisible. The whole command
                   was scanned as one string, "cd app" was found as the command
                   word, and a two-line call that cd'd and then removed a file
                   under verify/ passed straight through. A builder could have
                   deleted a test file that way for the entire life of the
                   guard.
       PHASE  Scripts / guard
       RECURRENCE  Fixed, with 9 new selftest checks covering the read/write
              pairs and the multi-line case. The CLASS - "a pattern used where
              a parser is required" - is still open elsewhere.

R2-02  Every phase workflow was unrunnable on a Windows checkout
       WHAT   All four .claude/workflows/*.js were CRLF in the working tree.
              The Workflow tool refuses a script containing control characters,
              so gp-phase0-ideas through gp-phase3-pack could not launch at
              all:
                "script contains control characters that would be hidden in
                 the approval dialog"
       ROOT CAUSE  git config core.autocrlf = true. The committed blobs are
              LF-clean (verified: git show HEAD:<path> has 0 CR bytes); the
              checkout rewrites them. Nothing in the repo pinned the ending.
       IMPACT TOTAL for this platform. Not one of the four documented phase
              entry points worked on a fresh Windows clone. The pipeline's
              whole published usage - the gp-phase* commands in README.md - was
              dead on arrival, and the error names control characters, not line
              endings, so it does not point at its own cause.
       FIX    Added .gitattributes pinning ".claude/workflows/*.js text eol=lf",
              and normalised the working copies.
       PHASE  Infrastructure / repo hygiene
       RECURRENCE  Fixed for these four files. HIGH for any NEW workflow or
              script added later - the .gitattributes rule is a path glob, and
              nothing checks that a new entry point is covered by it.
       SAME SHAPE AS  commit c7be9c4 (the guard's path pattern matching nothing
              on Windows) and B-01/B-02 in round 1. Three rounds, three
              platform-specific silent failures. This is now a pattern, not a
              coincidence: THE SELFTEST ONLY EVER EXERCISES THE MACHINE IT RUNS
              ON, and nothing checks that the repo's own entry points can be
              invoked at all.

R2-03  Workflow name resolution still injects control characters  [NOT FIXED]
       WHAT   After R2-02 was fixed and the file verified clean ASCII - every
              character scanned for Unicode categories Cc/Cf/Co/Cs/Zl/Zp and
              for codepoints above 126, zero hits, zero CR bytes, byte-identical
              to the git index blob - invoking the workflow BY NAME still fails
              the same control-character check. Invoking the SAME FILE by
              absolute scriptPath launches it successfully.
       CONCLUSION  The corruption is in the harness's name-resolution or
              permission-handler path, not in the file.
       WORKED AROUND  Every phase this round was launched by absolute
              scriptPath. The documented slash-command form remains broken.
       PHASE  Harness (outside this repo)
       RECURRENCE  CERTAIN until fixed upstream. Filed as harness feedback.
              README.md still documents the form that does not work.

R2-04  CLAUDE.md described a pipeline that no longer exists
       WHAT   The file every session loads first said "five agents, six
              scripts, three human gates" and listed 8 of the 15 scripts. The
              repo has 7 agents, 12+ scripts, 4 gates and two versioned flows.
              It documented the superseded Flow.md design as current, omitted
              flow 2 entirely, omitted Gate 0, omitted the frozen-spec
              mechanism, and gave the selftest count as 45 when it was 277.
       IMPACT Every agent and every session started from a wrong map. Unlike
              README.md (B-19), which is at least checked for its own check
              count, nothing verified CLAUDE.md against anything.
       FIX    Rewritten against the current architecture: both flows, every
              script with its step number, all four gates, rules 7 and 8,
              SPEC_FROZEN/revise, and the cut-marker return trap.
       PHASE  Documentation
       RECURRENCE  HIGH. Still nothing asserts CLAUDE.md's accuracy. The
              selftest pins README's check count and NOT CLAUDE.md's - the one
              number in it that could have been pinned for free was the one
              that had drifted by 232.

R2-05  The selftest was asserting on dead code
       WHAT   Two of the guard's checks tested the PATH_TOKEN regex directly.
              The R2-01 fix made that regex unreachable, so both checks would
              have kept passing while testing nothing.
       WHY IT MATTERED  The comment above them explained they existed to pin

       FIX    Retargeted at write_targets(), the live function, with 7

       RELATED  The same shape as the round-1 lesson "a fixture that encodes

       PHASE  Scripts / selftest
       RECURRENCE  MEDIUM. Nothing detects an assertion on an unreferenced
              symbol.

R2-06  Gate 1 rejected: five stated rules with no grading surface
       WHAT   gate1.json verdict=reject, blocking=2, unowned_blocking=1.
              Finding B1: the spec states five behaviours EXPLICITLY and no
              criterion exercises any of them. The Spec Breaker demonstrated

                1. "lost" before "won" branch order - the SESSION-3 HEADLINE

                   width*height - mines.length, the only input where the two

                   a 13-cell win threshold; c-3-6's gives 1 against 21.
                2. minesLeft may go below 0 - c-3-5 never plants a 4th flag on
                   a 3-mine board, so a clamp at zero is green.
                3. An empty clicks array is a valid 200 - never posted.
                4. 404 beats 400 - c-2-3 posts to no-such-board with a VALID
                   body, so body-first validation is green.
                5. flagged dedupe/default - c-3-4's flags are already distinct
                   and ascending.
       WHY IT MATTERS  These are not gaps the Builder must guess at. The spec
              is unambiguous. They are rules with NO GRADING SURFACE, which is
              worse, because they ship: a student writes the branches backwards
              and the pipeline reports 18/18.
       OWNER  nothing -> reject under the stopping rule.
       COST OF FIX  Low. Extend three existing criteria (c-2-3, c-3-3, c-3-5)
              rather than add new ones. Two of the five live in c-2-3, which
              has an empty cuts list, so no cut-dependency rework.
       SHAPE  This is round 1's "the criterion does not exercise the rule it is
              defending" recurring shape, now on its third project.

R2-07  Session 2 estimated at 38.5 of 40 minutes while carrying the heavy cut

R2-08  An agent wrote a report outside its lock and could not clean it up

       ASSESSMENT  The guard behaved exactly as designed and the agent behaved

              run a checker whose output path lies outside the subtree it is

       PHASE  Orchestrator / lock policy
       RECURRENCE  CERTAIN. Every flow-2 phase-1 run hits this, because
              red-first at step 5 always runs while verify/ is locked.


R2-09  revise is flow-1 shaped: it archives the spec and leaves the tests
       WHAT   cmd_revise moves spec.md, spec.json, lint.json, ambiguity.md and
              gate1.json into .pipeline/round-N/. It does NOT touch verify/ or
              redfirst.json. On flow 1 that is correct - the tests are written
              at step 6, AFTER Gate 1. On flow 2 the tests are written at step
              5, BEFORE Gate 1, so a rejected round leaves a suite written
              against the spec that was just archived.
       THE CONSEQUENCE  Step 5's completion test is
                (5, (d / "verify").exists() and _ok_json(d / "redfirst.json"))
              with NO hash binding - unlike step 4, which does compare
              reviewed_spec_hash against the live spec. So the surviving files
              mark step 5 DONE for the next round. The Spec Writer rewrites the
              spec, the Breaker re-runs and rebinds, and then `next` jumps
              straight from step 4 to Gate 1. THE TESTS ARE NEVER REWRITTEN,
              and Gate 1 is asked to approve a round-2 spec graded by round-1
              tests.
       WHY IT IS WORSE THAN IT SOUNDS  The findings that force a revise are, by
              the stopping rule, findings no downstream checker owns - which in
              practice means "a rule with no criterion grading it". The fix is
              therefore almost always "extend criteria X, Y, Z". Those are
              exactly the criteria whose tests would be missing. B1's fix
              extends c-2-3, c-3-3 and c-3-5; the round-1 suite has no tests for
              any of the added cases. The repair to an ungraded rule would
              itself have shipped ungraded.
       HOW FOUND  Read while planning the rerun this round's rejection
              requires, then confirmed empirically: a flow-2 project rebuilt
              post-revise reported
                step 3 complete, step 4 -, step 5 COMPLETE, step 6 -
              with round-1 tests still on disk against a round-2 spec.
       FIX    cmd_revise now adds redfirst.json and verify/ to the archive list
              when st.flow == 2. Flow 1 is untouched, so an approved flow-1
              suite is never reached for. Pinned by test_revise_flow2 in the
              selftest (7 checks, including the flow-1 negative case).
       PHASE  Orchestrator / revise
       RECURRENCE  Fixed. The CLASS - "a flow-1 assumption surviving into flow
              2" - is open: the flow split versioned the STEP TABLE, and every
              script was audited against it, but revise's file list is not
              derived from the step table and so was never part of that audit.
              Worth grepping for other flow-1-shaped constants.
