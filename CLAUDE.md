# CLAUDE.md

## What this repo is

A guided-project production pipeline: seven agents, twelve scripts, four human gates.
Turns a stack the human gave into five ideas, a spec, a test suite, working code,
a student skeleton, and an instructor session guide.

**Humans decide. AI drafts. Scripts check.** An agent is used only where judgement
is needed; everything else is plain code.

See `requirements_doc.md` for the current design, `Flow.md` for the original one,
and `README.md` for usage.

## Two flows

Three projects shipped under the original twelve-step design, so it is versioned
rather than rewritten. Every script reads the flow off `state.json`; a state file
written before the split reads as flow 1.

| | flow 1 | flow 2 (default) |
|---|---|---|
| Steps | 12 | 16 (0-15) |
| Gates | 3 | 4, with Gate 0 on the idea |
| Tests written | step 6, after the code | step 5, before the code |
| Phases | spec, code, pack | idea, spec, code, pack |
| Projects | recipe-box, tip-split, habit-tracker | new ones |

`pipeline new <slug>` creates flow 2; `--flow 1` creates the old shape. The
checkers flow 2 added step aside on a flow-1 project rather than failing it
retroactively - pass `--force` to run one anyway.

## Project structure

```
pipeline/           # orchestrator + every script (Python)
  cli.py            # orchestrator CLI - the single entry point, see below
  state.py          # flow, phase, gate and retry state; 15-retry and 30-run caps
  spec_linter.py    # step 3 checker - spec format and rules
  gate1.py          # step 4 checker - the Gate 1 stopping rule
  redfirst.py       # step 5 checker - the tests must be able to fail
  test_runner.py    # step 7 checker - runs the test suite
  mutation.py       # step 8 checker - proves the suite can go red
  cutter.py         # step 10 - generates the student skeleton from cut markers
  leak_scan.py      # step 10 checker - no answer line in the student tree
  guide_linter.py   # step 11 checker - the instructor guide
  deploy_check.py   # step 12 - install, build, preview link
  code_check.py     # shape checks a criterion can name (e.g. utc-dates)
  guard.py          # PreToolUse hook - write locks and the frozen spec
  watchdog.py       # nightly replay of shipped test suites
  selftest.py       # 460 deterministic checks on the scripts
  templates/        # CONTRACT.md (spec.json shape), idea_template.md
  ui_core.py        # UI read model - what the pipeline's files mean, events, run ledger
  ui_runner.py      # UI execution - one script (CLI subprocess) or one agent (OpenRouter)
  orchestrator.py   # UI auto-run - which action is next, and where it must stop
  ui.py             # UI HTTP server; ui_static/ is the page
.claude/
  agents/           # idea-generator, spec-writer, spec-breaker, test-writer,
                    #   builder, verifier, pack-writer
  skills/           # skill prompt per agent, plus the gp-phase* workflows
projects/<slug>/    # one directory per guided project
  idea.md           # the picked idea (flow 2 writes ideas/ first)
  spec.md / spec.json  # the spec (prose for Gate 1 + machine contract)
  ambiguity.md      # spec breaker output, bound to the spec hash it read
  verify/           # the test suite
  app/              # built project code
  skeleton/         # generated by cutter.py, never hand-edited
  pack/             # instructor session guides
  .pipeline/        # state.json, LOCK, SPEC_FROZEN, round history
                    #   plus ui-events.jsonl, ui-runs.jsonl, ui-logs/,
                    #   ui-workflow.json - written by the UI, read by nothing else
  *.json            # each checker's report - lint, gate1, results, deploy, leak
fixtures/           # test fixtures for selftest
learning/lessons.md # lessons learned - every agent reads this
```

## Key commands

```bash
python3 -m pipeline new <slug> [--flow 1|2]   # scaffold
python3 -m pipeline stack <slug> --stack .. --sessions N --minutes M   # step 0
python3 -m pipeline next <slug>               # what step is next
python3 -m pipeline status <slug>             # gates, retries, tickets
python3 -m pipeline pick <slug> <n> -m ".."   # GATE 0 - the human picks an idea
python3 -m pipeline gate <slug> N approve|reject -m "reason"
python3 -m pipeline revise <slug>             # archive a rejected round, reset Gate 1
python3 -m pipeline lock <slug> app|verify|pack   # rule 3, before an agent step
python3 -m pipeline unlock <slug>
python3 -m pipeline dryrun <slug> --session N --minutes M --by <who>   # step 13
python3 -m pipeline ship <slug>
python3 -m pipeline watch                     # nightly watchdog
python3 -m pipeline feedback <slug> -m ".."   # step 15, re-enters at step 3
python3 -m pipeline.selftest                  # run 460 deterministic checks
python3 -m pipeline.ui                        # the UI, http://127.0.0.1:8765
```

The UI is a window onto the same CLI, not a second pipeline: it shells out to
these commands, runs each agent's own prompt and skill against OpenRouter, and
stops at every gate. See the UI section of `README.md`. It writes only
`.pipeline/ui-*.json*` and `.pipeline/ui-logs/`, which nothing else reads.

Per-step checkers: `ideas`, `lint`, `breaker begin|end`, `gate1-check`,
`redfirst`, `test`, `mutation`, `cut`, `leak`, `guide-lint`, `handover-checks`,
`deploy`, `spec-status`. `python3 -m pipeline --help` lists them all.

## Rules (enforced, not just documented)

1. Every agent has a checker. If nothing can check it, one try and a person reads it.
2. Spec Breaker != Spec Writer (separate agents).
3. The Builder cannot edit test files - `guard.py` PreToolUse hook + LOCK file, and
   `mutation.py` proves the suite it cannot edit actually bites.
   The guard sees Write/Edit calls and shell write commands. It does NOT see writes
   made inside an interpreter (`python -c`, a node script). Read it as raising the
   cost of an accident, not as a guarantee.
4. `skeleton/` is always generated by `cutter.py`, never hand-edited.
5. The orchestrator is plain code. No agent manages another agent - and no agent
   edits the pipeline. `guard.py` refuses writes to `pipeline/`, `.claude/` and
   `learning/` while any project holds a LOCK. An agent that finds a pipeline
   defect reports it and stops; a person fixes it between steps.
6. Retries cap at 15, then a ticket is raised (`state.py`). A *green* step that keeps
   re-running is a loop too: `step_runs` caps that at 30 and raises the same ticket.
7. A report must name the spec it read - `ambiguity.md` is bound to a spec hash and a
   stale report is rejected at Gate 1.
8. Gate 1 terminates: approve when every finding sits in a column a downstream checker
   owns, not when the blocking count reaches zero. An owner that can pass by *not
   running* owns a finding only conditionally - `gate1.json` lists those under
   `verify_later` with the report and flag that must be read later, because
   "owned" and "checked" are not the same claim.

## Two critical artifacts

- **`spec.json`** - machine contract read by linter, test writer, builder, verifier and
  cutter. Shape defined in `pipeline/templates/CONTRACT.md`. Frozen at Gate 1 by
  `.pipeline/SPEC_FROZEN`; `guard.py` refuses to write it after that, and `pipeline
  revise` is the way to reopen it.
- **Cut markers** - `// >>> CUT <id>` / `// <<< CUT <id>` in app code. Cutter replaces
  them with TODO hints from spec.json. Never put a function's only `return` inside a
  pair - the skeleton stops compiling.

## Working conventions

- Run `python3 -m pipeline.selftest` before trusting changes to any script. It asserts
  its own count against `README.md`, so add checks and the README number moves with them.
- Update `learning/lessons.md` between runs, never during one.
- Commit the approved spec before starting the code phase.
- Every agent reads `learning/lessons.md` before starting.
- The phases are independent human checkpoints - each stops at its gate and does not
  roll on into the next.
